# Contratti API (catalogo corrente)

**Stato:** canonico per l'elenco degli endpoint esistenti · **Verificato su:** `main` (2026-11-23, D-07). I contratti per milestone sono nell'archivio storico non pubblicato ([ADR-0018](../architecture/decisions/0018-launch-repository-and-docs-archive.md)); in caso di dubbio prevale il codice.

Fonti: rotte in `apps/api/src/modules/<risorsa>/routes.ts`, schemi in [`packages/schemas/src`](../../packages/schemas/src), catena in [`apps/api/src/app.ts`](../../apps/api/src/app.ts).

## Regole comuni

- Base: `/api/v1`. Unica rotta pubblica: `GET /api/health`.
- Autenticazione obbligatoria su tutto `/api/v1` ([SECURITY](SECURITY.md)).
- Tutte le rotte di dominio, tranne `/me` (con `/me/places`) e `/workspaces`, richiedono `?workspaceId=`; la membership è verificata in un solo punto (`middleware/workspace.ts`). Workspace inesistente o altrui → **404**. Ruolo `viewer` = sola lettura.
- Mutazioni: corpo JSON obbligatorio (`Content-Type: application/json`, anche `{}` per DELETE e comandi), massimo 64 KiB.
- Validazione: input Zod quasi sempre `.strict()`; anche le risposte sono validate con gli schemi condivisi, **tranne** `/me`, `/workspaces`, `/overview` (schemi esistenti ma non applicati).
- Errori: `{ "error": { "code", "message", "requestId", "issues?" } }`. Codici: `validation_error`, `unauthenticated`, `forbidden`, `not_found`, `conflict`, `payload_too_large`, `unsupported_media_type`, `csrf_rejected`, `rate_limited` (definito, mai usato), `auth_misconfigured`, `internal_error`. I messaggi sono in italiano; i client si basano sul codice.
- Idempotenza (pipeline, note, documenti, colloqui, attività): id generato dal client + impronta SHA-256 della richiesta canonica; replay → 200, stesso id con contenuto diverso → 409.
- Concorrenza: niente colonne di versione; confronto e scambio (`expectedFrom` per la pipeline, `expectedUpdatedAt` per le attività, stato osservato per i colloqui, colonna di origine per gli spostamenti). Conflitto → 409.
- Paginazione: offset (`page`, `pageSize` ≤ 50) per `/opportunities`; cursore opaco per timeline, note (facoltativo) e attività.
- Ordinamento manuale: posizioni intere a intervalli (`POSITION_GAP = 1024`) con ribilanciamento ([ADR-0008](decisions/0008-kanban-ordering-and-board-loading.md)).

## Rotte aggiunte in v1

| Risorsa     | Metodo e percorso              | Schemi (input → output)                                            | Note                                                                   |
| ----------- | ------------------------------ | ------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| candidature | `GET /cards/:id/applications`  | → `applicationsResponse`                                           | dalla più recente; `current`, snapshot più recente                     |
|             | `POST /cards/:id/applications` | `createApplicationInput` → `applicationMutationResponse` (201/200) | nuova candidatura se non ce n'è una aperta; idempotente per `id`       |
|             | `PATCH /applications/:id`      | `updateApplicationInput` → `applicationMutationResponse`           | solo `appliedOn` e `channel`; lo stato si cambia con la pipeline       |
| opportunità | `GET /opportunities?scope=`    | `scope` ∈ `all` · `inbox` · `applications`                         | Opportunity Center                                                     |
| insights    | `GET /insights`                | → `insightsResponse`                                               | formule in `packages/shared/src/insights.ts`                           |
| calendario  | `GET /calendar?from=&to=`      | `calendarQuery` → `calendarResponse`                               | colloqui, attività con scadenza, scadenze degli annunci; max 62 giorni |
| export      | `GET /export`                  | → `workspaceExport`                                                | JSON versionato `jobward-export` v1, `Content-Disposition: attachment` |

La pipeline (`POST /cards/:id/pipeline`) crea la candidatura n. 1 con snapshot al primo avanzamento di un'opportunità che non ne ha; poi aggiorna sempre la candidatura corrente.

## Risorse assenti

Autenticazione applicativa (login, logout, registrazione, sessioni) · preferenze/impostazioni lato server · feed attività del workspace · modifica/eliminazione del workspace e gestione dei membri · contatti · notifiche · caricamento di file.

## Regola di manutenzione

Una rotta nuova o modificata aggiorna questo catalogo nello stesso commit; il test `security-hardening` enumera le rotte e verifica che siano protette. Contratti futuri (Smart Workspace, API pubbliche) si documentano qui quando entrano in `main`.
